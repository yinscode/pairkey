# Findings (read with leaky-donor-amp-claude.output.txt, the primitive layer)
# 1. The amplification appears unchanged at the exact call site signing uses:
#    accept = 2^-j for j unknown correlation-secret bits. The gate's single
#    failure variant (AbortProtocolAndBanReceiver) is what dsg.rs:303 maps to
#    SignError::AbortProtocolAndBanParty, which lifecycle.rs:121-124 maps to
#    QuarantinePeer. So a detected extension cheat quarantines the pairing.
# 2. No incremental oracle. Flipping x alone, or one t-row alone, accepted 0 of
#    16384 each. There is no cheap per-bit probe: any accepted injection requires
#    the attacker to already account for all but j bits of the secret, which is
#    the j-probe of part A. The extension check does not hand out bits.
# 3. Expected bits confirmed per surviving attempt is j*2^-j, peaking near 0.5 at
#    j in {1,2}. But a j-probe presupposes 256-j known bits, and the only
#    bootstrap is the setup selective-abort (about one bit per accepted donor,
#    one-shot, itself quarantine-risking). From that one bit the only available
#    probe is j~=255, accepted with probability about 2^-255.
# 4. No cross-donor accumulation (part C, 0 of 16384): bits learned against one
#    donor are worthless against the next.
#
# Accumulation conclusion: j stays about 255-256 over a donor's whole life; j=0
# is unreachable. Reuse across up to 100 signatures does not let an attacker
# grind the secret, because (2) there is no incremental oracle and (1) the first
# attributable miss quarantines the pairing. The 100-use and 600-second bounds
# therefore cap the pad-reuse window and availability, not the number of cheat
# attempts, which quarantine already caps at about one per pairing.
