02 / THE PROTOCOL

Put the rules
next to the key.

Your chosen source proves each request. Optional Solana policy and program logic add rules. Both signers check permission before your application receives a verifiable signature.

01

Make permission programmable.

Approve exact requests from an account, passkey or OIDC/OAuth identity. Add persistent rules, or let a Solana program evaluate logic and commit decisions that consume state.

02

2 independent TEE signers.

Two separate shares. Two independent authorization checks. PairKey’s architecture requires both signers to participate in every signature.

03

Your rules.
Two approval paths.

OFF-CHAIN SIGNING PATH

No per-message
approval transaction.

A wallet, passkey or OIDC/OAuth proof authorizes exact bytes. For immutable programs, each signer can evaluate pairkey_approve through read-only Solana simulation. Both signers check current permission without broadcasting an approval transaction.

  authenticate caller + exact request
  return policy.allows(input), input.digest

EXACT-OPERATION APPROVAL

Commit a program
decision on-chain.

Use pairkey_approve_commit when your Solana program must consume an allowance or update state. It records the exact approval in the same transaction; both signers check the finalized decision before signing.

ILLUSTRATIVE PROGRAM LOGIC · STATE-CHANGING

  authenticate caller + exact request
  require policy.allows(call)
  require allowance > 0
  decrement allowance
  record approval via gateway CPI

What makes a key programmable?

The source proves each exact request. Optional Solana policy restricts destinations, paths and payloads; a program can add application logic or consume state through an on-chain commit. Both signers independently enforce the current decision.

Why two independent signers?

PairKey distributes signing power across two parties. Each holds a separate key share and independently checks authorization. The protocol produces a signature without assembling the full private key. Read the security model →

How does multichain signing work?

One authorization model connects to FROST Ed25519, DKLS23 ECDSA, FROST RedPallas, and FROST secp256k1. Your application uses the resulting signature with its destination network. Explore chain integrations →

What can I build with PairKey?

Start with a Solana account or program. Integrate passkeys or OIDC/OAuth identities with bound ephemeral keys. Add persistent rules or state-consuming program approvals when your workflow needs them. Choose your source →
