PAIRKEY / DEVELOPER GUIDE

Build with
programmable keys.

PairKey connects Solana program authority to two-party signing. A controller program approves an operation or grants a scoped session. Both signers independently check finalized authorization and jointly produce a signature for your application.

Local developer preview. The target architecture uses two independent TEE signers. Current demos run separate local processes with mock attestation. They do not establish hardware protection or production readiness. Use local test assets only.

Run the local program demo

From the PairKey repository root, use Rust 1.88.0 with rustfmt and Clippy, Python 3.12+, and curl. The installer supplies the pinned Solana, Anvil, and SBF tools locally.

python3 scripts/install-ci-tools.py
source .local/ci-tools/env.sh
bash experiments/silence-dkls23/bootstrap.sh build --release --locked
cargo fetch --locked
bash scripts/build-programs.sh
cargo build --workspace --features pairkey-worker/dev-simulation --locked
bash scripts/demo-program-jobs.sh

The demo starts local services, exercises program-authorized signing and EVM sessions, and runs restart, cancellation, and freeze cases. Expect several minutes, including deliberate rate-limit waits. A complete validation gate is available through bash scripts/ci.sh.

Public evidence is written beneath .local/. That directory also contains private development roots and identity material; only selected public reports are suitable for sharing.

Connect your controller program

  1. Register a namespace. Make your controller program’s PDA the authority and enroll the signer identities.
  2. Enroll the signing key. For DKLS23 or RedPallas, use Client::signing_key and verify both pinned identities and the returned certificate.
  3. Approve the operation. Construct a canonical intent and COMMIT. Your controller publishes the exact approval through registry CPI, then the application waits for finalization.
  4. Request a signature. Call Client::submit_intent, then poll_intent or wait_intent. The SDK verifies signatures and both identity receipts against your request.
  5. Execute separately. Submit the signed transaction to its destination. The coordinator does not broadcast it for you.

A runnable Rust client lives in sdk/examples/program_jobs.rs. It takes a JSON configuration for endpoints, identity pins, a key request, payload, and fresh attempt ID; it assumes an already registered program-controlled namespace.

Authorize a session

For supported Solana and EVM native transfers, a session grants bounded permission to a delegate. The grant binds the signing account, destination, recipient, per-operation limit, policy version, and expiration. EVM grants additionally bound gas price and total fees.

Eligible session-only requests do not need a new Solana authorization transaction for each signature. Zero per-signature Solana transaction fees means precisely that: grant creation, revocation, destination execution, and infrastructure still have costs. Production service pricing has not been established.

Both signers still check fresh control state. A policy requiring COMMIT+SESSION needs an exact on-chain approval as well. RedPallas currently requires COMMIT. Total spending budgets, EVM contract calls, and EVM simulation are not implemented.

Solidity integration is planned. Solana remains the sole authorization control plane; an EVM contract cannot currently replace the Solana controller.

Handle results, retries, and cancellation

DKLS23 and RedPallas requests use POST /jobs with a signing envelope. Poll GET /jobs/:id, subscribe at GET /jobs/:id/events, or request cancellation through POST /jobs/:id/cancel.

  • Resubmitting the exact request recovers its retained job ID and any completed result. This does not trigger another signing operation while that result remains retained.
  • After a coordinator restart, interrupted jobs fail with may_have_signed: true. They never automatically resume.
  • A fresh attempt is an explicit application decision. Reconcile destination execution before retrying; a new signing attempt does not create a new transaction nonce.
  • Cancellation cannot retract already produced output. Neither can a later session revocation.
  • These durable result guarantees apply to the multi-suite job envelope. The legacy Ed25519 result cache remains memory-only.

The repository guide docs/program-jobs-and-lifecycle.md specifies retention, admission bounds, rate-limit handling, persisted incident latches, and restart semantics.

What is available?

  • Solana: FROST Ed25519 signing, local transfers, program authorization, constrained sessions and simulation.
  • EVM: DKLS23 ECDSA, local legacy EIP-155 native transfers, and scoped native-transfer sessions. Contract calls, ERC-20, and EIP-1559 adapters are not implemented.
  • Zcash: FROST RedPallas signatures verified through Orchard SpendAuth verification. Transaction assembly, proofs, wallet operations, and end-to-end execution are not implemented.
  • NEAR: Its Ed25519 signature family is compatible with an implemented scheme. A NEAR transaction adapter and end-to-end integration remain planned.
  • Credentials: Service-key and local passkey assertion verification exist. Complete passkey onboarding and OIDC with ephemeral keys remain future work.

Production gates include independent TEE/provider validation, protected entropy, rollback resistance, independent cryptographic review, and root recovery. Local tests do not establish these properties.

“The full private key never exists” describes intended protocol execution: participants create and use separate shares without assembling a full key. It is not a guarantee against extraction of a complete threshold of shares. Thresholds and TEEs have distinct assumptions.

The architecture targets lower authorization overhead through sessions. There is no published apples-to-apples benchmark establishing lower end-to-end cost or latency than NEAR Chain Signatures or Turnkey.

Read the architecture

In the repository, start with docs/program-jobs-and-lifecycle.md, docs/multi-suite-signing.md, and docs/implementation-status.md. Earlier architecture proposals must be read together with the latest implementation evidence.

The comparison on the landing page uses the standard request flow in NEAR’s Chain Signatures documentation and the signing and policy model in Turnkey’s architecture whitepaper. NEAR supports multichain outputs; it is not limited to signing NEAR transactions. Turnkey uses multiple enclave services; it is not accurately described as a single-TEE system.
