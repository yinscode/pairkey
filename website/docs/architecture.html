One authority. Two signers.

Solana programs govern permission. Two participants enforce that authority while jointly producing a signature.

Source → derive → sign

Source: a Solana program controls authority through its PDA, or a Solana account approves directly. Solana remains the sole control plane. Passkeys and OAuth/OIDC are planned application entry points into this authority model, not alternative control chains. Local passkey assertion verification exists; complete onboarding, account binding, and OIDC with ephemeral-key delegation remain integration work.

Derive: the authority’s namespace, destination, and account path identify distinct public keys. Use separate paths for separate accounts and separate destination contexts for separate chains. The resulting public key can be formatted into an address where the chain’s address scheme allows it; Zcash wallet addresses require additional wallet components. Ed25519 supports offline public derivation. New multi-suite keys require enrollment with both signers.

Sign: approve exact bytes or use an eligible scoped session, then submit the signing request to PairKey. Both signers check authority and participate with their separate shares. The application receives a signature and verifies the signer receipts. The target architecture places the participants in two independent TEEs; the public demo currently runs development processes.

Follow one signing request

  1. ApplicationConstructs the exact destination operation and its canonical intent.
  2. Solana controller + registryRegisters authority, publishes approvals, grants sessions, and records freezes or revocations.
  3. CoordinatorAdmits a job and routes encrypted protocol messages between the two signers.
  4. Signer A + signer BIndependently check current authority and participate with separate shares and fresh signing state.
  5. Application + destinationVerify the signature and receipts, then submit the transaction separately.

Shares throughout the protocol

The design uses separate key shares without assembling a complete private key. FROST Ed25519, DKLS23 ECDSA, FROST RedPallas, and Bitcoin FROST secp256k1 provide different signing schemes under the same application authorization model.

Current local FROST construction derives each participant’s share from its own root. The DKLS path wraps Spike D. New multi-suite keys require signer enrollment; the existing Ed25519 SDK’s offline public derivation is a separate capability.

The target deployment places the two signing parties in independent TEEs. See Security & status for the current local implementation and unresolved construction/provider assumptions.

Two authorization paths

Exact approval: the controller publishes a COMMIT for the exact bytes. Signers wait for finalized authority and check it before releasing signing output.

Scoped delegation: an existing session permits eligible operations within its registered bounds. A session-only request avoids a new control-chain authorization transaction, while current-state reads remain necessary.

Neither path makes cross-chain execution atomic. The coordinator does not submit destination transactions, and chain replay rules remain part of application correctness.

Authority at issuance

Workers order observed negative controls and their final authorization checks with local issuance locks. If a freeze or revocation is recorded first, subsequent issuance refuses. An already issued signature can still be delivered or used afterward.

The local lock does not fence cloned machines or replicas. Finalized observation freshness and production restart/bootstrap assumptions are part of the security boundary.
