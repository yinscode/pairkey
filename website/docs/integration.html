Connect your controller program

  1. Register a namespace. Make your controller program’s PDA the authority and enroll the signer identities.
  2. Enroll the signing key. For DKLS23 or RedPallas, use Client::signing_key and verify both pinned identities and the returned certificate.
  3. Approve the operation. Construct a canonical intent and COMMIT. Your controller publishes the exact approval through registry CPI, then the application waits for finalization.
  4. Request a signature. Call Client::submit_intent, then poll_intent or wait_intent. The SDK verifies signatures and both identity receipts against your request.
  5. Execute separately. Submit the signed transaction to its destination. The coordinator does not broadcast it for you.

A runnable Rust client lives in sdk/examples/program_jobs.rs. It takes a JSON configuration for endpoints, identity pins, a key request, payload, and fresh attempt ID; it assumes an already registered program-controlled namespace.

Bind the exact operation

Construct a canonical Intent containing the enrolled key and payload. Create the registry Commit over intent.bytes(). The controller program uses registry CPI to publish that approval; a plain HTTP request cannot grant authority.

Wait for finalized Solana approval and check that the transaction succeeded before submitting the signing job. Changing the payload, destination nonce, or signing bytes requires the corresponding authorization.

Use the Rust example

Read or download program_jobs.rs ↗. Run it from the repository with an application configuration:

cargo run -p pairkey-sdk --example program_jobs --locked -- APP_CONFIG.json

The example assumes a registered namespace controlled by the example-controller PDA. It enrolls a key, builds a COMMIT, submits a CPI approval, waits for finalization, submits a durable job, and verifies the returned signature.

coordinator / solana_rpc
Endpoints of your local coordinator and Solana RPC.
owner_keypair
Local path to the enrolled example-controller owner keypair. Keep the file private.
identities
The two pinned signer public identities, represented as 32-byte arrays.
key / payload
A serialized KeyRequest for the existing registration, account path, and suite, plus the suite-specific payload.
request_id / attempt_id
32-byte identifiers. Use a fresh unpredictable attempt ID for each explicit retry.

This is an application configuration contract, not a universal ready-made JSON file: registration values, identities, and key paths must come from your enrolled local environment.

Verify before use

The SDK verifies the returned key certificate, signature, and both identity-signed receipts against the original request. The current receipts are development assertions, not hardware attestation. Destination submission remains the application’s responsibility.

Keep Solana as the control plane

The current application path uses a Solana controller program. Account controllers remain supported as compatibility flows. Solidity integration is planned; an EVM contract is not currently a direct PairKey controller. See scoped sessions for delegate access.
