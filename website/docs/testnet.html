Build and deploy

From the repository root, install the pinned tools with python3 scripts/install-ci-tools.py if needed, then run:

bash scripts/demo-testnet.sh addresses
bash scripts/demo-testnet.sh build
bash scripts/demo-testnet.sh verify
# Fund the printed owner with devnet SOL before deploying.
bash scripts/demo-testnet.sh deploy
bash scripts/demo-testnet.sh serve

Open http://127.0.0.1:4180/demo. The backend serves the website and API on one origin. A static server on port 4173 only serves the website; it does not run the backend.

The script creates dedicated owner and program keypairs in .local/testnet-demo. It never selects your global Solana wallet. Build-time PAIRKEY_REGISTRY_ID and PAIRKEY_CONTROLLER_ID must match the deployed programs; the script applies them to both SBF programs and host binaries. Default builds retain the original local-validator program IDs.

Dedicated Solana RPC

For reliable signing, put a dedicated Solana devnet HTTPS RPC URL in .local/testnet-demo/solana-rpc-url, restrict the file to mode 0600, and restart the backend. It uses this endpoint for both signers and the control plane, and verifies the devnet genesis. The optional file is private and ignored by Git; never put a provider API key in website code or a tracked configuration. Without it, the backend uses the public devnet endpoint, which can rate-limit signing.

Fund the Solana authority

  1. Fund the printed Solana owner with devnet SOL using the Solana faucet. Around 10 devnet SOL is a useful initial allocation for program deployment, account rent, and transaction fees; actual deployment rent depends on binary size. Faucet limits may require multiple grants. Run the deploy command after funding.
  2. Start the backend. It registers the development signer set, enrolls message-signing namespaces and keys for both authority types, plus the existing transfer namespace.
  3. Optional, legacy transfer API only: copy the resulting PairKey EVM address from the page and send it approximately 0.002 ETH on Base Sepolia. This must be Base Sepolia test ETH, not Ethereum Sepolia ETH or mainnet funds. See Base network information for the testnet and funding resources.

The networks are fixed: Solana devnet genesis EtWTRABZaYq6iMfeYKouRu166VU2xqa1wcaWoxPkrZBG and Base Sepolia chain ID 84532. The backend checks them at startup and before each mutation.

Sign a message

  1. Choose a Solana program or the dedicated demo Solana account as authority.
  2. Choose Solana, EVM, Zcash, or NEAR. Inspect the derived public key and exact signing envelope.
  3. Choose Approve & sign. The authority publishes an exact-message COMMIT on Solana devnet. Both signers independently check finalized approval before signing.
  4. Inspect the combined signature and both verified signer receipts.
  5. Choose Verify signature to perform a new cryptographic check. Editing the signed message should make verification fail.

No session is used and no destination transaction is broadcast. Only the Solana approval requires test tokens. Read the message formats and walkthrough before integrating a chain-specific application.

Existing transfer API

The earlier program-controlled Base Sepolia transfer API remains available for operator testing. Its grant, transfer, revoke, and retry operations are separate from the message namespaces. Message signing cannot use those transfer session grants. Only the legacy transfer flow needs Base Sepolia test ETH.

Demo limits and custody

The backend binds to loopback, checks Host and Origin, accepts JSON with a custom same-origin header, signs bounded, domain-separated message envelopes after exact-message approval, and exposes no RPC proxy. The legacy transfer API permits only two fixed recipients; its alternate recipient is a generated test address without a retained spending key.

Grants last 1–10 minutes and allow at most 0.00001 test ETH per transfer. The signed execution-fee cap is 0.0001 test ETH and maximum gas price is 3 gwei. Base native transfers use exactly 21,000 execution gas, and the backend checks that the fixed recipient has no deployed code. Base charges additional L1 data and operator fees. The backend queries its GasPriceOracle, doubles those extra fee estimates for headroom, and rejects a total estimate above 0.0001 test ETH. It reserves that full fee allowance per operation. This is a local preflight estimate, not a protocol-enforced cap on changing network fees. See Base network fees.

A conservative backend budget reserves up to 0.01 test ETH across this state directory's lifetime and never refunds a reservation; at most 256 operations are retained. These are local demo limits, not a protocol-level cumulative session budget. Avoid concurrent external transactions from the enrolled EVM address.

Signer roots, delegate credentials, owner key, and durable journals remain in the ignored, private .local/testnet-demo directory. The browser never receives these secrets. Both signers run as development processes on this machine: receipts explicitly report hardware_backed: false. This is not a deployed pair of independent TEEs. The demo programs remain upgradeable by the dedicated owner.

Timeouts, restarts, and reconciliation

Every browser mutation has an idempotency ID. The backend serializes operations and persists the signing request before submission and the raw transaction before broadcast. A timeout may mean a transaction or signature already exists. An uncertain operation blocks new signing requests; grants and revocations remain available; a process restart marks unfinished operations for reconciliation. Do not delete the state directory or submit fresh signing attempts to work around that lock.

Inspect the saved Solana signature, coordinator job, raw Base transaction, and transaction hash in the private journal and chain explorers. Recovery requires operator review in this initial demo. There is no automatic retry, nonce replacement, or unlock endpoint. The explicit retry action can recover a terminal-failed signing job only when no raw transaction or transaction hash was saved, all uncertain signing attempts concern the identical intent, the original nonce is still unused, and the current session authorizes it. It starts a fresh MPC attempt while preserving the exact chain, nonce, recipient, amount, gas, and signing bytes. Only one transaction with that sender and nonce can execute on the canonical chain. Once a receipt matches a nonzero canonical L2 block hash and block number, matching uncertain attempts are resolved. This confirms L2 inclusion, not Ethereum L1 finality. A setup transaction's saved signature is checked again at startup before enrollment continues. The three service ports are persisted and must remain available across restarts because the coordinator journal binds the worker endpoints. Back up the entire private directory together; restoring stale state is not supported.

Local API

GET /api/status reports setup, addresses, balances, session state, and recent operations. POST /api/operations accepts sign_message with authority (program or account), chain (solana, evm, zcash, or near), message (1–256 UTF-8 bytes, not whitespace only), and a 32-character hexadecimal id. Legacy grant, transfer, revoke, and operator-only retry remain available. Send Content-Type: application/json and X-PairKey-Demo: 1. GET /api/operations/:id returns the persisted operation. Reusing an ID with different parameters fails. A retry uses {"action":"retry","id":"<new 32-hex ID>","original_id":"<failed operation ID>"}; it is deliberately not exposed as a one-click transfer button.

POST /api/verify accepts chain, public_key_hex, signed_message, and signature_hex. It verifies the supplied bytes without using a saved success flag or private signing keys.

The hosted demo uses HTTPS and proxy authentication; the backend remains on loopback. It is a shared, operator-funded development demo. This owner-controlled backend is not an open multi-user service. A public demo needs authentication, per-user namespaces and budgets, request limits, dedicated service operation, and independently deployed signers. Keep this server on loopback.
