Your Solana wallet controls the keys. PairKey’s hosted signers produce signatures after you approve each message.

Try it with your wallet

Connect Phantom or Solflare in devnet mode. This creates a namespace controlled by your connected account. It does not use the shared demo authority.

Use a devnet wallet with about 0.05 devnet SOL for registration and several approvals. Your wallet will ask you to sign Solana transactions.

Use it in your application

Copy the browser client into your application and provide @solana/web3.js v1. No PairKey processes run in your application.

import * as web3 from '@solana/web3.js';
import { PairKey } from './hosted-client.mjs';

const pairkey = new PairKey({ web3 });
const wallet = window.phantom.solana;
await wallet.connect();

const namespace = await pairkey.onboard(wallet);
const key = await pairkey.key(namespace, 'solana', [0]);
const approval = await pairkey.prepare(namespace, wallet, {
  chain: 'solana', path: [0], message: 'Hello from my application.'
});
await pairkey.approve(namespace, wallet, approval);
const { job_id } = await pairkey.submit(approval);
const result = await pairkey.wait(job_id);
console.log(key.public_key_hex, result.signature_hex);

What your wallet authorizes

The first transaction registers your namespace. Subsequent signing approvals bind the namespace, destination, path, request ID and exact message bytes. Our gateway requires your wallet’s signature; an HTTP request or knowledge of your address does not authorize signing.

You do not need to deploy a Solana program. Signing and finality take place asynchronously; your application receives the signature after both signers finish.

Set the rules for this account

This quickstart starts with per-message wallet approval. Every signing request needs a finalized Commit from your account; no additional policy setup is required. Loading a public key does not grant permission to sign.

Your account can also authorize a registered PairKey policy through a Solana transaction. The account policy guide shows the SDK instruction builder and explains versions, optional credentials, and supported session grants. The hosted quickstart currently submits exact-message approvals, without session or access-proof fields.

For custom application rules—such as a governance vote, an operation allowlist, or state-dependent approval—use a program-controlled namespace. The program enforces those rules before approving. Frontend restrictions alone do not constrain the controller wallet, and switching to a program creates a distinct namespace and keys.

Verify and keep the request

The browser’s Verify button asks the service to recompute verification using the returned public key, exact message, and signature. The API also returns both signer receipts. Applications can independently verify Ed25519, EIP-191, RedPallas, or the PairKey BIP-340 message format using the signing integrations and Rust SDK. The offline Rust verifier checks the signature and both signer receipts using a saved transcript.

Save the namespace registration, chain, path, approval request and job ID. Poll the same job after a timeout; do not automatically create a new signing request. “Recover last job” retrieves the saved job or resubmits the identical prepared request if its response was lost. The gateway checks finality and returns the existing job when one already exists.

How addresses are scoped

Your authority scopes a namespace. Within it, the destination, signature scheme, and numeric path select the key. The default namespace ID is 32 zero bytes; specify another 32-byte ID when your application needs separate namespaces. Keep the same deployment and namespace metadata when recovering a key.

The UI displays a Solana public key, a NEAR ed25519: public-key identifier, or an EVM address where applicable. Zcash and Bitcoin display signing public keys; this guide does not construct shielded addresses, NEAR named accounts, or transaction payloads.
