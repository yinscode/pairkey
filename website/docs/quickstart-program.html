How the program authorizes signing

The program below is the controller used by this example. Its rule is simple: the wallet that scopes the PDA must sign every request. Your application can replace that rule with its own policy.

  1. Check the request: accept only the gateway’s Register and Commit instructions.
  2. Check the owner: require the wallet’s Solana transaction signature and derive its expected PDA under this program.
  3. Check the gateway: require the pinned PairKey gateway address and an executable program account.
  4. Authorize through CPI: forward the request with invoke_signed. Solana grants signer privileges to this program’s PDA using its seeds and bump.

Register binds a namespace to the PDA. Commit approves a particular signing request. Once that approval is finalized, each hosted signer checks it before participating in signing. The resulting signature is fetched from the API.

//! Minimal developer-owned controller for PairKey's hosted devnet gateway.
//! Each wallet controls a separate PDA. Replace the owner check with your app's rules.
#![allow(unexpected_cfgs, deprecated)]
use solana_program::{
    account_info::{next_account_info, AccountInfo},
    entrypoint::ProgramResult,
    instruction::{AccountMeta, Instruction},
    program::invoke_signed,
    program_error::ProgramError,
    pubkey::Pubkey,
};
solana_program::entrypoint!(process_instruction);
// Pin the intended gateway. Verify this against https://pairkey.com/api/v1/config.
const GATEWAY: Pubkey = solana_program::pubkey!("rsYu5jyioN9YjWcj58houJ4AYnWKWwjTtpG8hSMw1QZ");
pub fn process_instruction(
    program: &Pubkey,
    accounts: &[AccountInfo],
    data: &[u8],
) -> ProgramResult {
    // Gateway v1 Borsh instruction tags: Register=1, Commit=2.
    if !matches!(data.first(), Some(1 | 2)) || data.len() > 1600 {
        return Err(ProgramError::InvalidInstructionData);
    }
    let mut iter = accounts.iter();
    let owner = next_account_info(&mut iter)?;
    let authority = next_account_info(&mut iter)?;
    let gateway = next_account_info(&mut iter)?;
    // APPLICATION LOGIC: the wallet that scopes this PDA must approve every call.
    if !owner.is_signer {
        return Err(ProgramError::MissingRequiredSignature);
    }
    let (expected, bump) =
        Pubkey::find_program_address(&[b"controller", owner.key.as_ref()], program);
    if *authority.key != expected || *gateway.key != GATEWAY || !gateway.executable {
        return Err(ProgramError::InvalidArgument);
    }
    let rest: Vec<_> = iter.cloned().collect();
    let mut metas = vec![
        AccountMeta::new(*owner.key, true),
        AccountMeta::new_readonly(expected, true),
    ];
    metas.extend(rest.iter().map(|a| {
        if a.is_writable {
            AccountMeta::new(*a.key, false)
        } else {
            AccountMeta::new_readonly(*a.key, false)
        }
    }));
    let ix = Instruction {
        program_id: GATEWAY,
        accounts: metas,
        data: data.to_vec(),
    };
    let mut infos = vec![owner.clone(), authority.clone(), gateway.clone()];
    infos.extend(rest);
    invoke_signed(
        &ix,
        &infos,
        &[&[b"controller", owner.key.as_ref(), &[bump]]],
    )
}

The APPLICATION LOGIC comment marks where you add your rules—for example, requiring a vote, checking a balance, or validating an application state transition. For a business-specific approval, also construct or validate the exact Commit fields, including the intended key and message commitment. The example forwards these fields because its policy is explicitly “the owner approves this request.”

Deploy your application logic

Use an existing program or start with the standalone controller template. The template requires the owner wallet to sign and derives an authority PDA from ["controller", owner_public_key] under your deployed program ID. Each owner gets a separate authority.

Its gateway address is pinned to the current hosted devnet deployment. Compare it with service configuration before deploying.

# Build and deploy your program using your Solana tooling.
# No PairKey workers, coordinator, or gateway deployment is needed.
unzip hosted-controller.zip
cd hosted-controller
cargo build-sbf --sbf-out-dir target/deploy
solana program deploy --url devnet --keypair YOUR_DEVNET_WALLET.json \
  target/deploy/pairkey_hosted_controller_example.so

Read the controller source. Replace the marked owner check with your application’s rules. When authorizing a specific business operation, construct or validate its expected COMMIT fields in your program; do not treat an arbitrary caller-provided hash as an approved business operation.

Connect your application

Copy the browser client into your application and provide @solana/web3.js v1.

import * as web3 from '@solana/web3.js';
import { PairKey } from './hosted-client.mjs';

const wallet = window.phantom.solana;
const pairkey = new PairKey({ web3 });
await wallet.connect();
// Try our devnet example; replace this with your program ID when ready.
const programId = 'AwALEPCSMeeK1HXhK9e1TTKQVZqAxp7EkzxAStqsY4Kz';
const controller = pairkey.controller(programId, wallet.publicKey);
const namespace = await pairkey.onboard(wallet, controller);
const key = await pairkey.key(namespace, 'evm', [0]);
const approval = await pairkey.prepare(namespace, wallet, {
  chain: 'evm', path: [0], message: 'Approved by my program.'
});
await pairkey.approve(namespace, wallet, approval);
const { job_id } = await pairkey.submit(approval);
const result = await pairkey.wait(job_id);

Integrate another program

Use your own PDA and provide { authority, wrapInstruction } to onboard. The adapter turns a returned gateway instruction into a call to your program. Your program validates application rules and performs invoke_signed with its own PDA seeds.

  1. Set a compute-unit limit of 1,400,000 (the browser client does this automatically). Keep the two signer-identity verification instructions at the transaction’s top level, before the registration CPI.
  2. For registration, invoke the gateway with the wallet payer and your PDA marked as the controller signer.
  3. For each message, validate your rules and invoke the gateway’s COMMIT instruction with that same PDA.
  4. Wait for finality, then submit the prepared signing request through the hosted API.

A program address alone cannot authorize a request. Solana must grant signer privileges to the PDA through your program’s CPI. Signing completes off-chain after the transaction; a signature is not returned synchronously to that instruction.

Add your program’s rules

The example’s rule is owner approval for every call. Each wallet controls a separate PDA, and the controller accepts only Register and Commit. The example program does not manage registered policies or session grants.

In your own controller, validate your application’s authenticated state and the exact operation before invoking Commit. For example, a governance decision should authorize a particular destination, path and message commitment—not any hash supplied by the caller. Read program rules and exact-request binding for the implementation pattern.

For registered PairKey policies, add explicitly authorized management instructions to your controller. Both signers then apply those requirements in addition to the approval. The policy field reference explains what exists in the core and which requirements the current hosted message API can supply.

Verify and keep the request

The browser’s Verify button asks the service to recompute verification using the returned public key, exact message, and signature. The API also returns both signer receipts. Applications can independently verify Ed25519, EIP-191, RedPallas, or the PairKey BIP-340 message format using the signing integrations and Rust SDK. The offline Rust verifier checks the signature and both signer receipts using a saved transcript.

Save the namespace registration, chain, path, approval request and job ID. Poll the same job after a timeout; do not automatically create a new signing request. “Recover last job” retrieves the saved job or resubmits the identical prepared request if its response was lost. The gateway checks finality and returns the existing job when one already exists.

How addresses are scoped

Your authority scopes a namespace. Within it, the destination, signature scheme, and numeric path select the key. The default namespace ID is 32 zero bytes; specify another 32-byte ID when your application needs separate namespaces. Keep the same deployment and namespace metadata when recovering a key.

The UI displays a Solana public key, a NEAR ed25519: public-key identifier, or an EVM address where applicable. Zcash and Bitcoin display signing public keys; this guide does not construct shielded addresses, NEAR named accounts, or transaction payloads.
