One authorization model, several signature schemes. Choose a message format that the relying application actually understands.

Hosted message signing

All five destinations use the same v2 hosted flow. Authenticate an exact request off-chain, or commit a program decision when state must be consumed. The result is a derived public key, signature and signer receipts. Destination transactions are not constructed or broadcast by this message API.

Solana and NEAR commit raw UTF-8 message bytes. EVM, Zcash and Bitcoin commit a typed signing intent containing the derived key and message. Policy limits apply to those canonical committed bytes.

Solana · FROST Ed25519

The hosted message signature verifies over the exact raw message bytes using the derived Ed25519 key, displayed in base58. It is not automatically a Solana transaction signature. The older local transaction adapter handles constrained native transfers and transfer sessions separately.

EVM · DKLS23 secp256k1

The hosted adapter signs EIP-191 personal-sign messages: the worker hashes the standard message prefix and exact bytes itself. The approved intent binds Base Sepolia chain ID 84532. The output is a 65-byte compact ECDSA signature with recovery ID 0 or 1; software expecting 27 or 28 must convert the last byte.

EIP-191 itself does not bind a chain ID. If the relying application needs chain-specific replay protection, include and validate that domain in the message too. EIP-712, arbitrary contract calls, ERC-20 and EIP-1559 are not implemented by this message adapter. The older local native-transfer adapter uses canonical legacy EIP-155 transactions.

Zcash · FROST RedPallas

The adapter signs the exact message using RedPallas and verifies it through Orchard SpendAuth RedDSA verification. The displayed public key is a verification key, not a complete shielded wallet address. Note management, transaction construction, proofs and a complete Orchard spending flow remain separate work.

NEAR · FROST Ed25519

The adapter uses a destination-separated Ed25519 key, displayed with NEAR’s ed25519: prefix. It signs the exact raw bytes. This is not NEP-413, a named NEAR account or a NEAR transaction. An application needs the appropriate NEAR payload, nonce and broadcast integration for those uses.

Bitcoin · FROST secp256k1 (BIP-340)

The adapter uses frost-secp256k1-tr, applying the BIP-341 no-script TapTweak and even-Y normalization. It returns a 32-byte x-only output public key and a 64-byte r || s BIP-340 signature, independently checked with k256.

The signed digest is SHA-256 of SHA256(tag) || SHA256(tag) || Borsh(network, message), with tag PairKey/BitcoinMessage/v1. The hosted context is Bitcoin testnet. This custom message format is not BIP-322, Bitcoin Core signmessage or a transaction sighash. No Bitcoin RPC or test BTC is needed for this message demo.

Use and verify the result

Use the hosted SDK to prepare canonical approvals; use hosted::offchain::verify_result in Rust or the offline verifier to verify the original approval, key and both receipts. The page’s Verify button performs a fresh service-side signature check; it is not independent verification of the service.

For transaction execution, construct the correct chain-specific bytes, authorize those bytes, verify the result and broadcast separately. A generic message signature neither requires broadcasting nor implies transaction support. Transfer-session grants cannot authorize arbitrary messages.
