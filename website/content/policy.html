No registration or policy setup required to start

V2 establishes public namespace metadata without registering an account on-chain. With no saved rules, every message still requires exact-request authentication. A read error is never treated as “no policy.” Once you create rules, their current revision remains authoritative.

Save policy on Solana and approve ordinary messages off-chain. This avoids per-message authorization transaction fees and approval-account rent. There is still RPC, service and signing work. Fully off-chain policy storage is deferred: an owner signature alone cannot prove that a policy is the latest revision.

Creating or editing rules is a separate Solana transaction for every source. A new or enlarged rules account may require rent; same-size edits reuse it. Service, RPC and destination costs are separate from Solana authorization fees.

Account policy: create and edit

Your wallet authorizes edits with a Solana transaction signature. The policy address is derived from ["rules", namespace_digest] under the gateway. No prior namespace registration is required. The released PairKeyClient from Quickstart: Account does not expose standard-rule management. For a custom integration, follow the low-level policy implementation: read the current rules, prepare revision current + 1, check the returned update and instructions, and send the owner-signed Solana transaction.

Creating or enlarging rules can require rent funding. Same-size edits reuse the account’s deposit and pay only transaction fees. A policy update does not require threshold signing. The controller can change its own policy; use a program with stricter governance if the controller itself must be constrained.

Passkey and OIDC/OAuth policy

The released PairKeyClient supports passkey and OIDC/OAuth signing, but it does not export standard-rule edits, passkeyAssertion or ephemeralIdentity as public package APIs. The flows below describe custom integrations with the low-level implementation.

Passkey: identify the namespace by the credential’s compressed P-256 public key, RP ID and origin. For ordinary signing, authenticate a bound ephemeral Ed25519 key. For a policy edit, prepare the next rules revision and request a fresh WebAuthn assertion directly over that update's challenge. Check the returned instructions before sending the fee-payer transaction. Solana’s native P-256 verification checks owner authorization; no MPC signature or per-edit ephemeral-key registration is needed. The fee payer gains no policy authority. Setting rules is optional before the first passkey-approved message.

OIDC/OAuth: the issuer, audience and subject define the identity. Create the bound ephemeral key before preparing the update, and authenticate with its binding challenge as the OIDC nonce. The ephemeral key signs the exact update. Both signers independently verify the configured issuer’s ID token and attest the update; only those public attestations go on-chain. No provider is enabled implicitly. JWTs and passkey assertions go only to private authentication endpoints; they are not included in public receipts or persisted job records. See the identity flow.

Program policy: evaluate or consume

Your program owns its application rules. Its management instruction authenticates the owner or governance process, verifies state account ownership and PDAs, and updates a monotonic revision. The recommended v2 scope stores one policy per owner and namespace under ["pairkey-policy", owner, namespace_digest]. Compatible shared scope uses ["pairkey-policy", owner] only when every namespace should intentionally share one policy and revision.

max_payload_bytesMaximum canonical committed payload size, at most 1,232 bytes.
payload_prefixRequired byte prefix of that payload, at most 128 bytes. Empty imposes no prefix.
disabledRefuse signing while true.

Solana and NEAR commit raw message bytes. EVM, Zcash and Bitcoin commit a serialized signing intent containing the key and typed message. A text prefix is therefore not a universal message filter across suites. Hosted raw messages are limited to 256 UTF-8 bytes independently of these policy bounds.

Update or stop permission

Read the current rules, choose the next revision and authorize the exact update. A stale edit is refused rather than silently rebased. Set disabled: true to stop new authorization; later re-enable through another authorized revision. There is no delete-to-default policy fallback.

Each signer checks fresh policy before signing and before releasing output. An observed newer policy fences stale prepared requests. These checks do not retract an issued signature or make destination execution atomic with a policy change. Keep destination nonces and replay rules in your application.

Sessions are deferred for v2

Bound ephemeral keys authenticate requests; they do not bypass policy or create a scoped session. The older native-transfer API retains its registered Policy, COMMIT, grant and revoke formats. It has different fields and supported payloads. New standard rules also constrain that legacy authorization path; switching endpoints does not remove them. An existing customized legacy policy needs explicit migration to v2 rules. See legacy sessions.
