Define who may sign, what they may sign, and which approvals are required. Solana records the authority; both PairKey signers check it before participating.

Two places to enforce rules

Rule layerWhere it runsWhat it controls
Your application programA Solana instruction before gateway CPIBusiness logic: owner approval, governance, allowed operations, application state, and the exact request it will authorize.
Registered PairKey policyStored in the gateway; evaluated independently by both signersRequired Commit approval, eligible sessions, additional credentials, and supported simulation checks.

A program can use both layers. An account can approve requests directly and administer a registered policy. A browser check alone is not an enforced signing rule: another client can skip it.

Start with per-message approval

Both hosted quickstarts use the default rule: every message needs a finalized Solana Commit. An account authorizes it with its wallet signature; a program authorizes it through a PDA after its own checks. No separate policy transaction is needed for this default.

The public hosted API currently prepares registrations and exact-message approvals. It does not offer a policy editor, session-grant API, or request fields for session/access proofs. Custom program checks before Commit work with the hosted flow today. Advanced registered requirements must be paired with a signing interface that supplies their proofs; the quickstart does not bypass them.

Set rules in a Solana program

  1. Define the authority. Derive a PDA under your program and register it as the namespace controller.
  2. Authenticate the caller and state. Verify required transaction signers, program ownership of state accounts, and the expected state PDAs.
  3. Validate the operation. Derive or check the expected destination, path and exact message or canonical intent from authenticated application state. Apply your business rules before approving that request.
  4. Commit through CPI. Pass only the validated Commit to the pinned gateway, using invoke_signed with your PDA seeds.

For example, a governance program can store an approved Commit in its own state, then permit CPI only when the proposal has passed and the supplied Commit matches it. This illustrative check belongs inside the program, after validating the proposal account and vote result:

// Excerpt: proposal is authenticated, program-owned application state.
// expected_commit was constructed from the operation approved by governance.
if !proposal.passed || requested_commit != proposal.expected_commit {
    return Err(ProgramError::InvalidArgument);
}
// Construct the gateway Commit instruction with requested_commit,
// then invoke_signed using this program's authority PDA seeds.

Do not populate expected_commit from an unchecked caller argument. If the rule is about a recipient or amount, parse and validate the typed operation and bind its exact signing bytes. Arbitrary message text such as “send 1 ETH” is not a transfer payload and does not provide a spending policy.

The quickstart controller demonstrates the simplest rule: the wallet that scopes the PDA must approve each call. Its instruction allowlist contains only Register and Commit. To administer registered policies, grants, revocation or freezing from a PDA, implement explicit authenticated management instructions in your own controller. Do not simply open the forwarding allowlist to every caller.

Set rules for a Solana account

With an account-controlled namespace, your wallet is the controller. By default, it signs each exact-message approval directly. The wallet also authorizes policy updates and supported session grants on Solana. The wallet paying rent may be separate from the controller; paying a fee does not grant signing authority.

The Rust SDK exposes gateway instruction builders. This excerpt constructs the first explicit Commit-only policy for an already registered account namespace. It does not submit a transaction:

use pairkey_types::policy::Policy;

let policy = Policy {
    version: 1, // First stored policy; later updates use previous version + 1.
    allow_session: false,
    require_commit: true,
    require_session: false,
    access: None,
    simulation: None,
};
let instruction = pairkey_sdk::set_policy(
    payer_public_key,
    controller_wallet_public_key,
    &registration,
    policy,
);
// Put instruction into a Solana transaction for the intended gateway deployment.
// The payer and controller sign (one signature if they are the same wallet).
// Submit on Solana devnet and wait for successful finalization.

The SDK’s gateway program ID must match the namespace and hosted deployment configuration. Build your application’s transaction with the SDK or an equivalent instruction adapter; no PairKey worker needs to run on the developer’s machine. The hosted browser helper currently has no setPolicy() method.

To enforce application rules such as a governance decision or a custom allowlist before every approval, use a program-controlled namespace. A direct account signature proves that the controller approved the request; it does not cause the gateway to execute arbitrary application logic. This program namespace derives different keys from the account namespace.

Registered policy fields

FieldMeaning
versionThe implicit default is version 0. The first stored policy is version 1; every update must increment by exactly one.
require_commitRequire finalized approval of the exact operation. A request without a session still needs Commit even if this flag is false.
allow_sessionPermit a supported, valid session grant. This does not create a grant.
require_sessionRequire a session as well. This may only be true when sessions are allowed.
accessOptional additional service-key or passkey credential proof, bound to the operation and policy version.
simulationOptional constrained Solana native-transfer simulation against a pinned immutable executable. Not a general-purpose predicate engine.

A valid stored policy cannot disable Commit while also disallowing sessions. Required proofs compose: selecting another client or endpoint does not waive them. Passkey assertion verification exists in the core; hosted passkey onboarding and OAuth/OIDC delegation are separate integration work.

Delegation and spending limits

For supported Solana and EVM native-transfer adapters, a session grant binds a delegate credential, destination/path, recipient, per-operation amount cap, validity window and policy version. EVM grants also pin the enrolled key, chain ID, gas-price cap and total-fee cap. Current grant validity windows are at most 24 hours.

Use pairkey_sdk::grant_session or grant_evm_session after enabling sessions in the policy. Accounts authorize these instructions directly; program controllers invoke them through authenticated management CPI. The delegate must provide an operation-bound proof with each signing request.

These are transfer sessions, not arbitrary-message sessions. They do not cover every chain or the hosted message quickstarts. Amount limits apply to each operation; cumulative budgets and general EVM contract-call policies are not implemented. See Scoped sessions for the supported combinations.

Change, revoke, or stop permission

Publish policy changes with the next version and wait for finality. Signers require the current policy version; old grants and proofs no longer match it. To revoke a grant, use revoke_session or revoke_evm_session. Revocation is permanent for that grant ID. To stop the namespace, use freeze with the controller’s authorization.

For program authorities, each management action needs a corresponding controller instruction; the public quickstart example does not expose these. The current controller governs policy updates, so a wallet-controlled policy is not an immutable restriction against that same wallet. Put stricter change-control rules in a program if you need them.

Freezing, revocation, or a policy change affects subsequent authorization checks. It cannot retract a signature already issued. An exact Commit is not a guarantee of one destination execution: use appropriate destination nonces and replay rules.
