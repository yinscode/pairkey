Sign your first message

  1. Select My Solana account, Solana program or, when configured, Google account · OIDC preview. No namespace registration transaction is needed.
  2. For a program, select the hosted example or enter your own v2 program and set its policy. For Google, select your account first; a second Google prompt will approve the exact message after the provider app is available to your account.
  3. Choose Solana, EVM, Zcash, NEAR or Bitcoin and a path index. Load and inspect the derived public key.
  4. Enter up to 256 UTF-8 bytes. Approve the exact request with a wallet message signature or a nonce-bound Google ID token. Program on-chain mode also asks for a transaction.
  5. Follow the two signers and inspect the returned signature and receipts.
  6. Select Verify signature. Change a message character and verify again to see the mismatch.

Choose a source

An account source uses the connected wallet as authority. A program source uses an owner-scoped PDA and authenticated application rules. Google uses the configured OIDC issuer, client ID and stable subject. Each source has its own namespace and keys. The hosted example program selects on-chain mode to support upgradeable code; immutable programs can use read-only off-chain evaluation.

The new flow has no sessions. Passkey identity support is in the SDK and local tests; the public demo has no browser credential-registration flow yet. Policy changes and on-chain commits need devnet SOL. Ordinary account and Google off-chain message approvals need no SOL or destination funds. See Quickstart: Google for the two-prompt binding flow.

Five destinations, four signature schemes

Solana and NEAR use FROST Ed25519; EVM uses DKLS23 ECDSA with EIP-191; Zcash uses FROST RedPallas; Bitcoin uses FROST secp256k1 and a BIP-340 signature over PairKey’s tagged message digest. Solana and NEAR have distinct destination-separated keys.

The verification box shows the exact signed message. Approval additionally binds identity, key, destination/path, request ID, rules revision and expiry. The audit trail includes that public request. Read Signing integrations for replay domains, key formats and transaction-integration boundaries.

Progress follows evidence

A wallet prompt is not signer completion. Both signer cards remain pending during authorization, show joint work after job admission, and become verified only after the hosted result and matching receipt pair return. Individual MPC round timings are not reported.

History is retained in this browser tab. Saved results are labelled as saved until recovered; a stored success flag does not establish fresh receipt verification. Failure after submission can be uncertain. “Recover last submitted job” reads the saved attempt without another wallet approval, commit or signing round.

Fresh signature verification

The Verify button asks the service to recompute verification from the displayed message, public key and signature. Editing an input invalidates the previous verification status. This checks mathematical signature validity, not an independent trust anchor for the service.

For independent verification of the original approval, signature and both signer receipts, save the transcript from the audit trail and use the offline Rust verifier with trusted deployment identities.

Use your signature

A message signature can be verified by a relying application off-chain. It is not a transaction and does not require broadcasting. To execute a chain transaction, construct and authorize the correct chain-specific payload and submit separately.
