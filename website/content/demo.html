Sign your first message

  1. Select Solana program or Demo Solana account. Both paths use the dedicated demo owner; no visitor wallet is connected.
  2. Choose Solana, EVM, Zcash, NEAR, or Bitcoin. Inspect the derived public key and signature scheme.
  3. Enter up to 256 UTF-8 bytes and expand Exact signing envelope. The envelope binds destination, authority, controller address and a unique request ID alongside your text.
  4. Select Approve & sign. The selected authority approves the exact signing operation on Solana devnet. Signing starts only after finalization.
  5. Watch the two signers check authority and cooperate in threshold signing. The output is a signature, not a broadcast transaction.
  6. Select Verify signature. Change a character in the editable verification envelope and verify again to see the mismatch.

Program or account authority

The program path invokes the registry through the example controller's PDA. The account path uses the dedicated demo owner's Solana transaction signature directly. Each authority has its own message-signing namespace and keys. These are separate from the older transfer-session namespace.

This version uses per-message COMMIT approval. There is no session bypass: every new request needs a new finalized Solana approval. Message sessions, visitor wallet connection, and OAuth delegation are future integration work. The core's existing native-transfer sessions do not authorize arbitrary messages.

Five destinations, four signing schemes

  • Solana: FROST Ed25519 over the displayed UTF-8 envelope; a base58 public key.
  • EVM: DKLS23 secp256k1 ECDSA using EIP-191 personal_sign. The worker hashes the prefix and exact message bytes itself. The demo binds Base Sepolia chain ID 84532 in the approved intent and displayed envelope. The output uses a 65-byte compact signature with recovery ID 0 or 1; tools expecting 27 or 28 must convert that final byte. The page shows the public key and corresponding EVM address.
  • Zcash: FROST RedPallas over the displayed envelope. The displayed key is a verification key, not a complete Zcash wallet address or an Orchard spend authorization.
  • NEAR: FROST Ed25519 with a destination-separated derived key, shown with its ed25519: prefix. The envelope is a PairKey demonstration format, not NEP-413, a registered NEAR account or a NEAR transaction.
  • Bitcoin: FROST secp256k1 using the Taproot-compatible frost-secp256k1-tr suite. The page shows a 32-byte x-only output key and a 64-byte BIP-340 Schnorr signature. Both shares receive the BIP-341 no-script TapTweak. Workers sign a tagged SHA-256 digest of the network and displayed envelope. This is a PairKey message format, not BIP-322, Bitcoin Core signmessage, or a transaction sighash. No Bitcoin RPC or test BTC is needed.

Changing destination or authority changes the derivation context. Solana and NEAR share a signature algorithm but use distinct derived keys. All raw Ed25519 and RedPallas inputs are explicitly visible. These envelopes cannot be treated as chain-native transactions.

Evidence-driven progress

Signer cards show joint signing in progress until verified identity-signed receipts arrive. The SDK verifies both receipts and the final signature before the result is labelled verified. Individual MPC round timing is not reported. Each card shows its signer identity and observed finalized Solana slot.

A backend preflight failure is distinct from a signer refusal. An uncertain outcome remains unresolved and blocks new signing. No fresh attempt is started automatically. Operation history preserves approvals, exact envelopes, public keys, signatures and receipts.

Fresh verification

The verification action submits the displayed chain, public-key bytes, envelope and signature to a stateless cryptographic verifier on the demo backend. It does not consult the saved success flag, require a private key, or submit a chain transaction. Editing the envelope, signature or public key invalidates the previous verification result. Verification establishes a mathematical signature match; authorization evidence is provided separately by the Solana approval and signer receipts.

Use your signature

Your application may verify a message off-chain, share it with a relying application, or use an appropriate chain-specific transaction flow. Arbitrary message signatures do not need broadcasting. This demo does not construct or broadcast destination transactions and spends only devnet SOL for setup and approvals.

Deployment

The demo runs two development signer processes, with hardware_backed: false. Independent TEE deployment remains separate. The hosted demo is public and uses shared, operator-funded development accounts. The migrated local state is an offline backup; never start it while the hosted instance runs.
