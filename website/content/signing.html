Choose the destination flow, then the signature scheme. A supported signature primitive is one part of a complete transaction integration.

Solana · FROST Ed25519

Local flows cover exact COMMIT approvals, program/CPI controllers, native transfers, scoped sessions, and constrained simulation. The session adapter accepts a canonical legacy message containing one System Program transfer, with the derived account as payer and signer.

Use the existing Ed25519 SDK flow, including Client::submit_authorized for policy-authorized requests. It is distinct from the DKLS23/RedPallas multi-suite envelope. Additional instructions, lookup tables, and extra signers require separate adapters.

EVM · DKLS23 ECDSA

The local adapter constructs and signs canonical legacy EIP-155 native transfers. It supports fixed gas limit 21,000, a nonzero recipient, no calldata, bounded chain ID, and u64 nonce, value, and gas price. Native transfers execute on local Anvil.

Exact approvals and scoped EVM sessions are supported. ERC-20 calls, arbitrary Solidity calls, EIP-1559, EIP-712, and Hyperliquid adapters are not implemented. Solana governs authority; EVM is a signing destination.

Zcash signing layer · FROST RedPallas

PairKey produces signatures verified through Orchard SpendAuth RedDSA verification using the Pallas generator. RedPallas currently requires an exact COMMIT approval.

A complete Orchard wallet is separate work: transaction assembly, note management, proofs, application replay semantics, and end-to-end execution are not included. RedPallas signature verification is not evidence of a complete Zcash transfer integration.

NEAR · integration planned

Ed25519 is compatible with an implemented signing family. A NEAR-specific transaction adapter, encoding and replay checks, broadcast flow, and end-to-end validation are still needed. The landing page’s multichain model describes signature-family reach, not a claim that every transaction adapter is shipped.

Select the right entry point

  • For existing Ed25519 account derivation and Solana policies, use the original SDK path.
  • For DKLS23/RedPallas, enroll through signing_key, submit an Intent through submit_intent, and verify through poll_intent or wait_intent.
  • Destination execution is always separate. Verify the signature, correct chain context, and destination nonce before broadcasting.
