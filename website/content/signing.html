Choose the destination flow, then the signature scheme. A supported signature primitive is one part of a complete transaction integration.

Use hosted message signing

The hosted quickstarts support Solana, EVM, Zcash, NEAR and Bitcoin message signing using your account or program authority. They select the corresponding scheme and return a derived public key, signature and signer receipts. Each message needs finalized Solana approval; these signatures are not automatically broadcast or interpreted as transactions.

The sections below describe the scheme-specific core and lower-level SDK integrations. Transfer-session policies apply only to their supported transaction adapters; see policy scope.

Solana · FROST Ed25519

Local flows cover exact COMMIT approvals, program/CPI controllers, native transfers, scoped sessions, and constrained simulation. The session adapter accepts a canonical legacy message containing one System Program transfer, with the derived account as payer and signer.

Use the existing Ed25519 SDK flow, including Client::submit_authorized for policy-authorized requests. It is distinct from the DKLS23/RedPallas/Bitcoin multi-suite envelope. Additional instructions, lookup tables, and extra signers require separate adapters.

EVM · DKLS23 ECDSA

The local adapter constructs and signs canonical legacy EIP-155 native transfers. It supports fixed gas limit 21,000, a nonzero recipient, no calldata, bounded chain ID, and u64 nonce, value, and gas price. Native transfers execute on local Anvil.

Exact approvals and scoped EVM sessions are supported. ERC-20 calls, arbitrary Solidity calls, EIP-1559, EIP-712, and Hyperliquid adapters are not implemented. Solana governs authority; EVM is a signing destination.

Zcash signing layer · FROST RedPallas

PairKey produces signatures verified through Orchard SpendAuth RedDSA verification using the Pallas generator. RedPallas currently requires an exact COMMIT approval.

A complete Orchard wallet is separate work: transaction assembly, note management, proofs, application replay semantics, and end-to-end execution are not included. RedPallas signature verification is not evidence of a complete Zcash transfer integration.

NEAR · FROST Ed25519

The demo signs messages with FROST Ed25519 and shows a NEAR-formatted public key. A NEAR-specific transaction adapter, encoding and replay checks, broadcast flow, and end-to-end validation are still needed. The landing page’s multichain model describes signature-family reach, not a claim that every transaction adapter is shipped.

Bitcoin · FROST secp256k1 (BIP-340)

The Bitcoin message adapter uses Suite::FrostSecp256k1Tr and Payload::BitcoinMessage through the multi-suite API. Two independently derived shares run Zcash Foundation’s Taproot-compatible FROST suite. Both key packages apply the BIP-341 no-script TapTweak and even-Y normalization. The final signature is independently verified with k256’s BIP-340 verifier.

The public key is x-only (32 bytes); the signature is r || s (64 bytes). The signed digest is SHA-256 of SHA256(tag) || SHA256(tag) || Borsh(network, message), with tag PairKey/BitcoinMessage/v1. Mainnet and testnet have separate destination contexts. Bitcoin messages require exact COMMIT approval; transfer sessions cannot authorize them.

This is message signing with a Taproot output key. BIP-322, PSBT handling, transaction sighashes, UTXO selection, fees, and Bitcoin broadcast remain separate work. The root-derived share setup is experimental, as are the existing research integrations; it is not a production security certification.

Select the right entry point

  • For hosted message signing, start with PairKey.onboard, key, prepare, approve, submit and wait in the browser client.
  • For existing Ed25519 account derivation and Solana policies, use the original SDK path.
  • For DKLS23/RedPallas/Bitcoin, enroll through signing_key, submit an Intent through submit_intent, and verify through poll_intent or wait_intent.
  • Destination execution is always separate. Verify the signature, correct chain context, and destination nonce before broadcasting.
