Keep your application’s rules in a Solana program. Authorize the PairKey gateway through a PDA, then retrieve a signature from our hosted signers.

Start with the hosted flow

The Quickstart: Program provides a deployed example, its complete Rust source, and an interactive signing flow. Try it with your wallet, then deploy a controller containing your own application logic. You do not need to run PairKey workers or a coordinator.

  1. Choose your authority PDA. The example uses ["controller", owner_public_key] under your program ID. Your program may use different seeds.
  2. Register its namespace. The hosted API prepares registration and both signer-identity verification instructions. Your program authorizes registration through CPI.
  3. Choose a destination and path. Enroll a derived public key through the hosted API. The namespace belongs to the PDA, not to the wallet paying its transaction fees.
  4. Approve an exact message. Your program checks its rules and invokes the gateway’s Commit instruction with the PDA as signer.
  5. Retrieve and verify. After Solana finality, submit the prepared request, poll its job, and verify the signature and receipts.

Connect the example controller

This browser excerpt uses the deployed owner-gated example and the hosted client. The wallet approves each Solana transaction; PairKey performs signing after the approval finalizes.

import * as web3 from '@solana/web3.js';
import { PairKey } from './hosted-client.mjs';

const pairkey = new PairKey({ web3 });
const wallet = window.phantom.solana;
await wallet.connect();

const programId = 'AwALEPCSMeeK1HXhK9e1TTKQVZqAxp7EkzxAStqsY4Kz';
const controller = pairkey.controller(programId, wallet.publicKey);
const namespace = await pairkey.onboard(wallet, controller);
const key = await pairkey.key(namespace, 'evm', [0]);
const approval = await pairkey.prepare(namespace, wallet, {
  chain: 'evm', path: [0], message: 'Approved by my program.'
});
await pairkey.approve(namespace, wallet, approval);
const { job_id } = await pairkey.submit(approval);
// Persist approval, key and job_id before waiting.
const result = await pairkey.wait(job_id);
const { valid } = await pairkey.verify(result);

Connect a different program

The supplied controller() adapter only implements the example template’s account layout and instruction format. For your own program, derive its authority PDA and supply { authority, wrapInstruction } to onboard. The wrapper receives a gateway instruction and returns the instruction that calls your program with the required application accounts and data.

// Application-specific adapter: implement these using your program's ABI.
const namespace = await pairkey.onboard(wallet, {
  authority: applicationAuthorityPda,
  wrapInstruction: gatewayInstruction =>
    buildApplicationInstruction(gatewayInstruction, applicationState)
});

Your program must validate the supplied state accounts, their ownership, PDA seeds, caller permissions, and the expected gateway. It then constructs the gateway CPI and uses invoke_signed with its authority seeds. Merely putting a program ID or PDA into an HTTP request grants no authority.

Keep the two Ed25519 signer-identity verification instructions at the transaction’s top level before registration CPI. The hosted client preserves them and sets the compute budget. Only the gateway registration or approval instruction is wrapped.

Bind your rules to the exact request

A Commit binds the registration digest, request ID, destination/path, message hash and byte length. Ed25519 approvals bind the signing bytes directly; multi-suite approvals bind the canonical signing intent containing the key and payload. Use the prepared approval for the request you intend to sign.

For application-specific rules, your program must independently construct or validate these fields against its own authenticated state and expected operation. A check such as “the caller supplied a hash” does not enforce an amount limit, recipient allowlist, or governance decision. The program policy guide explains where these checks belong.

The public template deliberately implements an owner-approval rule: an owner may register and approve messages for their own PDA. It is not a treasury policy, voting program, or policy administrator. Deploy a controller implementing those rules when your application needs them.

Finality, recovery, and verification

The hosted API requires finalized approval before it admits a signing job. Save the prepared request and returned job ID. Poll or resubmit that identical request after a transport timeout; do not generate a new approval just because the response was lost. Interrupted jobs may have signed and require reconciliation.

The browser Verify button recomputes signature verification on the hosted service. For independent verification, save the request, key response, completed result and pinned identities, then use the offline Rust verifier. It checks the signature and both signer receipts. Current identities are development assertions; hardware deployment status is documented in Security & status.

Message signing does not broadcast a destination transaction. A relying application can verify a message off-chain. For transaction execution, construct and authorize the appropriate chain-specific payload and handle submission separately.

Manage authority and policy

Solana is the control plane for both program-PDA and wallet-account authorities. Read Policy & rules for program checks, account-controlled registered policies, and the distinction between per-message approvals and session grants. EVM is a signing destination; Solidity contracts are not currently direct controllers.

Advanced: self-hosted Rust integrations

program_jobs.rs demonstrates the lower-level coordinator interface with canonical intents, explicit attempts, and receipt verification. It uses an already registered namespace, the repository example-controller ABI, a local owner keypair, identity pins, and coordinator/RPC endpoints. It is distinct from the hosted template above and is not required for hosted onboarding.

cargo run -p pairkey-sdk --example program_jobs --locked -- APP_CONFIG.json

Use the self-hosted API reference and local development guide for that configuration.
