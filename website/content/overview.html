Choose who controls a key, give it a purpose, approve one exact request, and receive a native signature from two independent signers.

New to PairKey? Follow the lifecycle below, then choose Account, Program, Passkey or OIDC. Each source reaches the same key and transaction APIs; the authorization proof is what changes.

The complete model

  1. Choose a sourceA wallet, Solana program, passkey or OIDC identity controls the namespace.
  2. Name the purposeA namespace such as org/acme/treasury creates a stable authority and policy boundary.
  3. Derive a keyThe namespace, destination chain and numeric path select a stable public key. No complete private key is assembled.
  4. Approve exactly one requestThe source authenticates the destination, path, payload commitment, request ID, expiry and current policy revision.
  5. Threshold signBoth signers independently verify the request and policy, then produce one chain-native signature.
  6. Send or recoverYour application broadcasts through its destination RPC. A saved job ID retrieves the original attempt after interruption.

Every source must approve every request even when no optional policy has been saved. Passkey and OIDC ephemeral keys authorize one request; they do not hold assets and do not change the stable destination address.

Give each key a purpose

Use a namespace for a business or security boundary and a numeric path for subaccounts governed together:

namespace: org/acme/treasury/solana
path [0]: operating account
path [1]: reserve account

The stable key is selected by the source identity, PairKey deployment, namespace, destination and path. Policy edits do not rotate it. Changing the source, namespace, destination or path selects another key. See Keys & namespaces.

One SDK after connection

await pairkey.connect({source, namespace, ...authentication});

const key = await pairkey.key({chain, path});
const signed = await pairkey.signMessage({chain, path, message});
const assembled = await pairkey.signTransaction({chain, path, transaction});
const sent = await pairkey.signAndSend({chain, path, transaction, ...rpc});
const recovered = await pairkey.recover(jobId);

signTransaction returns signed destination bytes without broadcasting. signAndSend uses the connection, RPC URL or broadcast callback provided by your application. PairKey's signing service does not choose or operate the destination RPC.

Authentication and policy are separate

Exact-request authentication proves who approved the operation. Optional standard rules restrict destination, path, payload size or availability. A program can additionally enforce application logic such as membership, recipient, amount, proposal state or a consumable budget. Setting or editing policy is an administrative transaction; it is not repeated before every signature.
