Programmable keys on multiple chains. Choose an authority, define its rules, and request a signature from two independent signers.

Start with your Solana account or your program. PairKey runs the signing infrastructure. The passkey guide and Google preview cover bound-identity approvals.

Source → derive → sign

A source identifies who controls a namespace. A Solana account authorizes an exact request with a wallet message signature. A program authenticates its caller and applies application rules. Passkey and OIDC identities authenticate a bound, short-lived Ed25519 key that signs the request. Solana stores optional persistent policy and program state.

Choose a destination and derivation path to obtain a public key. Both signers independently authenticate the request and enforce current rules before participating in threshold signing. The protocol uses separate key shares; it never assembles the full private key. The target deployment uses two independent TEEs; current development workers report their hardware status explicitly.

The concepts you need

Namespace
Public derivation context binding the authority, deployment and signer set. The v2 flow establishes metadata without a registration transaction.
Derivation path
A numeric path selecting a key inside the namespace and destination context. Paths are not independent compromise domains.
Exact approval
Authentication bound to the namespace, exact payload, destination/path, request ID, policy revision and expiry.
Policy
Optional, versioned rules stored in a reusable Solana account and enforced by both signers.
Off-chain approval
Request authentication and rule checks without broadcasting an authorization transaction. Programs use authenticated RPC simulation.
On-chain approval
A program transaction that changes application state and records its exact approval atomically through gateway CPI.
Job
A durable signing attempt with a stable ID and recoverable public results. It is not a destination transaction.

Development status

V2 supports message signing for Solana, EVM, Zcash, NEAR and Bitcoin. Typed transaction signing is implemented for Solana legacy/v0 messages, restricted EIP-155 EVM native transfers, and canonical NEAR transactions. Bitcoin PSBT/Taproot and Zcash transaction adapters remain open work. Sessions are deferred for this flow. Read transaction support and Security & status.
